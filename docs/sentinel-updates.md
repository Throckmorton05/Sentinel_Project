# Sentinel signed distribution updates

Revision `0.1.0-10` adds dedicated Sentinel-only updates and the current ISO
cleanup/branding steps: [update-controls-and-branding.md](update-controls-and-branding.md).

The subsequent `0.1.0-9` changes add opt-in ISO defaults, commission-marketplace
category coverage, installer branding, and an offline guide. Use
[the onboarding rebuild guide](iso-onboarding.md) for that revision's commands.

For GitHub hosting without a purchased domain, use
[github-updates.md](github-updates.md). That guide replaces the conventional
directory-hosting steps below with a signed flat GitHub Release channel; the
application/platform builds, installed-VM bootstrap and preservation checks
remain the same.

The installed system updates through APT. The bootable ISO remains an installer
snapshot: new users get a rebuilt ISO, and existing users get newer packages
without reinstalling. This supports updates within Kubuntu 26.04 amd64, not an
upgrade to a different Ubuntu release.

## Package layout

The original five matching packages remain the application release. A sixth,
`sentinel-platform`, contains the installed distribution helpers, protected
startup units, AdGuard/Starship/font vendors, wallpaper packages, editable
appearance defaults, Plymouth branding, and public repository trust.

Its version and `Depends: sentinel (= VERSION)` match the five-package build.
APT installs that release's packages in one transaction. Dpkg transactions are
not atomic: a failed/interrupted upgrade may need maintainer repair. The runtime
package already defers its restarts until package locks are released. Platform
service/binary changes require a reboot; the upgrade does not stop DNS itself.
The session guard may close the desktop during a backend restart. Save work
before updating and reboot afterwards, or use a scheduled update time.

Platform upgrades do not run account provisioning, generate new credentials,
replace lock settings or PINs, overwrite daily-limit/activity state, or reseed
user appearance files. Root service overrides are removed only when they match
recorded ISO copies; customized overrides remain and are reported for review.

`sen update-sys` and the existing automatic-update schedule use the same bounded,
unattended APT runner. Any index-refresh error aborts the update. Updates prohibit
removals and keep existing dpkg conffiles. Existing protected-package downgrade
and removal checks remain active. Scheduled updates record success and consider
rebooting only after the package operations succeed.

## 1. Create signing trust on the development laptop

These commands run on the development laptop, not the protected VM. Keep the
private key outside the project, ISO kit, hosting directory and upload ZIPs.
Use a strong passphrase and keep a separate secure backup of the key/revocation
certificate. The production key is not generated by the provided patch.

```bash
cd "$HOME/Sentinel_Project"
sudo apt-get install apt-utils gnupg
export GNUPGHOME="$HOME/.local/share/sentinel-release-gnupg"
install -d -m 700 "$GNUPGHOME"
gpg --quick-generate-key 'Sentinel Linux Archive <releases@sentinel.invalid>' ed25519 sign 2y
gpg --list-keys --fingerprint
```

The email is a key label, not a hosting address or email delivery endpoint.
Replace it with the release contact you intend to use before generating a real
release key. Copy the complete primary fingerprint from the output. Set the
real HTTPS repository URL; do not run the following with placeholder values.

```bash
SENTINEL_KEY_FPR='PASTE_FULL_PRIMARY_FINGERPRINT'
SENTINEL_APT_URL='https://YOUR_REAL_HOST/sentinel'
python3 packaging/iso/repository_config.py \
  --url "$SENTINEL_APT_URL" --signing-key "$SENTINEL_KEY_FPR" \
  --output configs/updates
```

This exports only the public key and validates the URL, fingerprint, source and
package pins. APT uses the repository-specific `Signed-By` keyring; signature
and metadata-expiry checks remain enabled. Only the six Sentinel package names
are pinned to this repository. No `apt-key`, `trusted=yes`, unsigned repository,
user-selected root installer, or generic root command is added.

Keep `configs/updates` for subsequent builds. The configuration exporter refuses
to overwrite an existing directory. Signing-key rotation and host changes must
be reviewed and shipped in a package signed with the currently trusted key
before the old key expires; do not silently swap keys on the server.

## 2. Build the updated packages

Apply the patch to the source project first. The changelog is advanced from
`0.1.0-7` to `0.1.0-8`; the upstream version remains `0.1.0`.

```bash
cd "$HOME/Sentinel_Project"
bash tools/build_debs.sh --reuse-inputs dist/debs/0.1.0-20261012-194756
```

Set the exact newly printed successful output folder. The full project on your
laptop has models, signed extensions and retained wheels; the small upload ZIP
intentionally does not contain everything required to build these real DEBs.

```bash
SENTINEL_DEBS='/full/path/to/new/successful/deb-build'
bash build.sh platform \
  --kit "$HOME/Sentinel_ISO_Build/sentinel-iso-kit" \
  --debs "$SENTINEL_DEBS" \
  --output "$HOME/Sentinel_ISO_Build/platform-0.1.0-8"
SENTINEL_PLATFORM="$HOME/Sentinel_ISO_Build/platform-0.1.0-8/sentinel-platform_0.1.0-8_amd64.deb"
```

Use the original complete verified kit on your laptop. The platform builder
checks it before using its pinned vendor binaries. It combines those inputs
with the current project helpers/configs, current font default, and new boot
artwork. It does not modify the old kit or its manifest. To refresh vendors,
review `vendor-lock.json`, prepare a new complete kit and use that kit instead.
Fastfetch remains its separately installed APT package.

## 3. Build and publish the signed APT repository

```bash
python3 packaging/iso/publish_repository.py \
  --debs "$SENTINEL_DEBS" --platform "$SENTINEL_PLATFORM" \
  --signing-key "$SENTINEL_KEY_FPR" \
  --output "$HOME/Sentinel_ISO_Build/repository-0.1.0-8"
```

Host the output's contents at the exact HTTPS URL configured above. The host must
serve `dists/` and `pool/` as ordinary static files, including large model and
runtime DEBs. It must not require a browser login. No hosting account, DNS, URL,
production key or public deployment has been configured by this patch.

For subsequent publications, use a new output path and `--previous` pointing to
the previous repository. This preserves older package files and immutable
`by-hash` indexes. Never publish different bytes under an existing package name,
version and architecture; the tool rejects this when given the previous repo.
Always increment the Debian revision for changed packages.

Publish new package files and `by-hash` indexes first, current package indexes
next, `Release`/`Release.gpg` next, and `InRelease` last. Retain previously served
immutable files for clients using an older signed index. Make `InRelease` a
single-file atomic replacement and use a short cache lifetime for it. Do not
upload your GPG home or any private state.

Signed metadata expires after 30 days by default. Re-run signing/publication
before expiry even when packages are unchanged (for example every two weeks).
Expired metadata intentionally prevents updates; it does not stop the installed
desktop or DNS service. No refresh automation has been created by this patch.

## 4. Enable the existing VM once, without reinstalling

Yesterday's ISO did not ship an APT source or archive key. Its user deliberately
has no administrator access, so a one-time authorized maintenance setup is
necessary to install that trust. This is not an end-user `sudo` feature.

Take a VM snapshot. Transfer the current `packaging/iso` helpers and public
`configs/updates` into an authorized root maintenance environment. If there is
no maintenance account, boot the existing installer/live ISO, mount the VM's
installed root filesystem, and enter its target chroot. We should choose the
mount/chroot commands from your actual `lsblk -f` output, particularly if the
VM has separate `/boot`, EFI or encrypted partitions. Do not rerun `build.sh
image`, `provision_install`, or the Calamares installer against the installation.

Inside that **installed target's root maintenance shell**, after the repository
is hosted and reachable:

```bash
python3 /path/to/packaging/iso/bootstrap_updates.py \
  --config /path/to/configs/updates \
  --fingerprint 'THE_PRIMARY_FINGERPRINT_FROM_YOUR_DEVELOPMENT_LAPTOP'
```

The helper verifies that this is an installed Sentinel Kubuntu 26.04 amd64
system, checks the independently supplied fingerprint, installs only public
repository trust, permits the named platform package through the old APT guard,
and asks authenticated APT to install it and the matching application release.
It preserves existing policy entries and installed state. A failed operation
returns an error; take its output to the maintenance harness for repair rather
than blindly retrying an interrupted dpkg transaction.

Reboot the VM. Subsequent updates run as the desktop user:

```bash
sen update-sys
```

The existing Portal update schedule uses the same repository. A backend update
can disconnect a GUI request while service processes restart; verify the package
versions and backend recovery after the transaction, then reboot if requested.

## 5. Ship update support in future ISOs

```bash
bash build.sh prepare --debs "$SENTINEL_DEBS" \
  --platform "$SENTINEL_PLATFORM" \
  --output "$HOME/Sentinel_ISO_Build/sentinel-iso-kit-0.1.0-8"
bash build.sh verify "$HOME/Sentinel_ISO_Build/sentinel-iso-kit-0.1.0-8"
```

Use that new complete kit inside Cubic. The platform DEB installs its own helpers
and units, so they are no longer unmanaged `/etc/systemd/system` copies. The
installer still creates the account and unique credentials once. Calamares
cleanup and the final provisioning hook are retained. The original kit remains
usable for provenance/vendor inputs and is not modified in place.

## Appearance and wallpapers

New installations get the editable 11-point Konsole default (previously 12).
Existing user files are intentionally preserved on update. To apply just the
new font size to an existing VM, run as its normal user:

```bash
kwriteconfig6 --file "$HOME/.local/share/konsole/Sentinel.profile" \
  --group Appearance --key Font 'JetBrainsMono Nerd Font,11,-1,5,50,0,0,0,0,0'
```

Close and reopen all Konsole windows. Verify Fastfetch at the VM's display scale.
Edit appearance with the normal user:

```bash
nvim "$HOME/.config/starship.toml"
nvim "$HOME/.config/rofi/config.rasi"
```

The update does not replace either file. Kate remains the default graphical text
editor. The existing palettes are retained. Wallpapers remain two named KDE
packages, each with four resolutions; the source index is
`assets/Screensavers/README.md`. They are static desktop/lock-screen backgrounds.
The new dark-gray Plymouth startup splash uses the existing white shield and
standard two-step password dialogue. The GRUB menu/security settings are not
changed by this splash update. The theme is rebuilt into initramfs during
platform configuration. Actual boot rendering, disk-password prompts, high DPI
and GPU behavior need VM/hardware verification.

## Installed-VM acceptance checks

Run the read-only checker as the VM's normal desktop user:

```bash
python3 /path/to/packaging/iso/vm_checks.py
```

It checks the protected account, Wayland session, privilege groups, required
services, appearance write access, private AdGuard paths, desktop denial of the
AdGuard control endpoint, and read-only Sentinel status/list commands. A PASS is
limited to that observed check; no read-only script proves behavioral blocking
or all possible login paths.

### Verify upgrades preserve state

In Unlocked or authorized Guardian mode, set a harmless saved preference, add a
test website/app block, and customize Starship/Rofi. Record current lock mode,
account UID, package versions, DNS status and custom appearance hashes. Upgrade
from `-7` through bootstrap to `-8`, reboot, and confirm all survive. Have the
root maintenance harness compare AdGuard credential file hashes without printing
contents. Confirm a newer package version is offered from the expected signed
origin, then repeat with a second test release. Test corrupted/unsigned/expired
metadata, a package checksum mismatch, and interrupted updates in disposable
snapshots. Do not deliberately enter irreversible Self Lock on a development VM
unless that test state is intended.

### Verify login lockdown

Code inspection found one desktop account, PAM account restrictions, one-login
limits, a logind session guard, KDE Wayland-only SDDM choices, disabled alternate
remote logins, and denied administrator groups/actions. Confirm these actually
apply in the installed VM. Test logout/login, alternate/TTY login attempts,
additional sessions, and stopping a required protection service using the
maintenance harness. The ordinary account must not gain a shell, second usable
desktop, root access, or an unprotected session. `loginctl list-sessions` may also
show the SDDM greeter; distinguish it from a second normal user's desktop.

### Test app blocking

Use a snapshot in Unlocked or authorized Guardian mode. Close Kate, then run:

```bash
sen app-block add-native iso-test-kate /usr/bin/kate --name 'Kate test'
sen app-block status
```

Attempt Kate through the menu, terminal and Rofi, and try an already-running
instance in a separate test. The block must actually apply, not merely appear in
the saved list. Verify other required apps remain usable. Then clean up:

```bash
sen app-block remove iso-test-kate
```

Kate must launch again. Test a supported Flatpak with its exact ID separately.
No behavioral app-blocking test was run on your installed VM from this session.

### Test boot services and desktop autostart

Create a small harmless Python service inside the VM user's home. It appends a
timestamp to `~/.local/state/sentinel-boot-test.log`, flushes it and stays alive.
Register it with `sen add-service boot-test /absolute/path/to/boot-test.py`, then
`sen enable-service boot-test`. Add Kate's desktop launcher with
`sen autostart-add org.kde.kate.desktop`. Reboot, login and verify the timestamp,
service status (`systemctl status sen-managed-boot-test.service`) and Kate window.
Services start at system boot as the unprivileged user; GUI autostart runs after
Plasma login. Clean up with `sen disable-service boot-test`,
`sen delete-service boot-test` and `sen autostart-remove org.kde.kate.desktop`.
Remove the disposable script/log. Use Unlocked/authorized Guardian mode so the
temporary test entries can be removed.

### Verify AdGuard enforcement

The ISO uses per-install random credentials, bcrypt hashes, a non-login DNS
account, loopback listeners, root-private API credentials, firewall denial of
ordinary-user API connections, and a read-only service sandbox except for its
config/state. This patch adds device/kernel/clock/control-group isolation,
namespace/realtime restrictions, native syscall architecture, restricted socket
families and a private umask. It does not regenerate existing credentials.

Verify DNS filtering before and after reboot/update, both IPv4/IPv6 queries,
explicit external-port-53 queries, and legitimate Sentinel policy changes through
the API. Check root-owned firewall rules in the maintenance harness. The new
sandbox still needs a real systemd/AdGuard runtime test. DNS transport controls do
not themselves solve arbitrary HTTPS proxies/tunnels; retain the existing ISO
security-scope limits when assessing release readiness.

## Validation in this development session

Tests use disposable package metadata and temp state; they do not install
packages or modify the host's system policy. The container runs Python 3.12,
not the target's Python 3.14; a complete production package build and Cubic/VM
boot test remain required on the development system.

The repository integration checks exercised real `dpkg-deb`, `apt-ftparchive`,
`gpgv`, and isolated APT index acquisition/candidate simulation. APT accepted
signed metadata and rejected tampering. GPG agent sockets are unavailable in
this container, so a disposable PGPy RSA signing adapter supplied the test
signatures; GPG export and APT/gpgv verification ran normally. Production GPG
signing/pinentry must be exercised on the developer machine. The standard suite
skips those agent-dependent signing tests here. No production key or repository
was created or published.

Run on the build laptop:

```bash
python3 -B -m unittest discover -s packaging/iso/tests -v
poetry run pytest sentinel/daemon/tests/test_custom_installer.py \
  sentinel/daemon/tests/test_apt_updates.py \

  sentinel/daemon/tests/test_sen_cli.py \
  sentinel/daemon/tests/test_app_blocker.py \
  sentinel/daemon/tests/test_autostart.py
```

App cleanup is deferred at your request. Extra approved Coding/Utilities packages
